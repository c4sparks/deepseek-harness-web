# 00 · 工程流程与规范（活文档总纲）

> 阶段：总则 · 自包含 · 维护者：插件维护者
> 覆盖：文档书写约定（元数据/骨架/更新记录/**禁止绝对路径**）、迭代维护流程、开发协作规范。集成自原模板 16/17 与既有约定。

## 1. 文档书写约定（所有文档适用）
### 1.1 元数据块（标题下第一段，`>` 引用）
```markdown
> 阶段：需求/设计/开发/测试/发布/总则 · 维护者：____
```
版本基线不以全局头部形式维护；正文引入/变更点用行内 `【v<插件版本> · dsh <版本>】` 标注，底部更新记录汇总版本与日期。
### 1.2 通用骨架
结构顺序：标题、元数据、目的/范围、主体章节、代码映射、已知缺口、维护提示、更新记录表。

**写作风格（🔒 文档干净清爽）**：
- 不用无关紧要的修饰符号、箭头（`→`、`↔`、`⬇`）与纯装饰图标/emoji；表顺序或流向一律用文字（如"之后""产物为""再…"）。
- 确需表示状态/流程转移时，用文字或用 `代码块` 呈现，不在正文堆箭头。
- 成对对应、键值、选型、清单等结构化信息优先用**表格**；简单列举才用列表。
- 指向 UI 真实控件/按钮的图标（如 🤖/🛡 指输入区按钮）可作控件名保留，仅当名称，不作装饰。
### 1.3 更新记录字段（每份文档底部）
| 日期时间 | 插件版本 | 变更 | 维护者 |
|---|---|---|---|
版本号直接写目标号（不标 `(dev)`）；文档更新记录（迭代过程）≠ CHANGELOG（已发布一条，`<版本> - <日期>`，存放于仓库根 `CHANGELOG.md`，不随包发布），两者都维护。
主体章节中的新增/修改/删除，应在对应行或小节标题直接标注 `【v<插件版本> · dsh <版本>】`（如 `【v0.1.4 · dsh 0.1.2-rc.1】`），用于在正文里定位“哪个能力是哪个版本引入的”；底部更新记录只做汇总，不再重复每个位置。

**更新记录只记内容与行为的变更**：纯文档整理——路径/编号调整、文档在目录间移动、引用指向的更新、章节重排——**不记**（这类动作自己知道即可，记了反而让人以为内容变了）。
### 1.4 路径书写约束（🔒 强制）
**文档内禁止本机绝对路径**：盘符绝对路径、含用户名路径、机器专属仓库路径一律不用。正确写法：相对路径（同仓 `src/dsh/`、`../`）或占位符（`<dsh 源码仓根>`、`<DSH_HOME>`、`<用户主目录>`）或纯功能语义（`dsh web`、`pnpm dsh web`）。

提交前必须查两类，**两类都要跑**：盘符/用户名类，以及「机器专属仓库目录名」类（后者无盘符无用户名，前者正则抓不到）。

**防「假通过」（🔒 强制，2026-09-10 补）**：检查命令会被某些 shell / 命令包装器**吞掉反斜杠**，模式退化成一串普通文本，恰好只匹配到规则那一行自己——表现为「有输出、看着像通过」，真实违规全部漏报。**判读标准：输出里除规则那一行之外还应有命中**；只有一行即未真跑对，改用下面不写字面反斜杠的写法。

```bash
# 盘符 / 用户名：十六进制构造反斜杠，绕开吞转义
BS=$(printf '%s' '5c' | xxd -r -p)
grep -rnE "[A-Za-z]:${BS}${BS}|Users${BS}${BS}|/home/|/Users/" docs src tmp

# 机器专属仓库目录名
grep -rnE "dsh_sources_code|other_dsh_plugins" docs src
```

### 1.5 编码约定（🔒 强制）
**所有文档/代码文件一律 UTF-8（无 BOM）**。历史教训：在中文系统用 Windows PowerShell 默认 `Get-Content`/`Set-Content` 改 UTF-8(无 BOM) 中文文件会按 GBK 误读造成乱码。
- 写入新文件：用支持 UTF-8 的编辑器/工具（本项目文档应无 BOM）。
- 命令行批改中文文件：**必须显式指定编码并避免 BOM**，不得依赖 shell 的默认编码（否则中文会按 GBK 误读）。
- 提交前可抽查：文件以 `EF BB BF` 开头则为带 BOM（不符合），正文无 `\uFFFD`/形如 `鈥�`/`鏂囨` 的乱码替换符。

### 1.6 插件标识书写约束（🔒 强制）
文档正文与代码注释不写本插件的扩展标识/发布者信息（`<publisher>.<name>`、市场名、具体 vsix 文件名）。需要引用时，用占位符（`<publisher>.<name>`、`<name>.vsix`）或统一称"本插件"；`package.json` 的 `name`/`publisher` 是发布元数据的唯一来源，正文与注释不重复。

### 1.7 文档引用方向与自足（🔒 强制）
**引用只能单向：细节文档可以引用 `design`，`design` 不能引用细节文档（也不引用其中的章节）。**

**细节文档与 `tmp/` 都不在本仓库**（细节文档已移至独立的文档仓库；`tmp/` 被 `.gitignore` 忽略），对克隆仓库的人是不存在的路径 —— design 里写「详见某细节文档」等于给一条死链。

- design 的结论必须**自足**：要指就指同样入库的其它设计文档（按编号，如 `04`、`06`），或代码路径（`src/…`、`webview/…`）。
- 同样**别用「见上文 / 细节见某段」把内容推给别处** —— 把内容写出来。发布记录尤其要自足：读者不该为了看懂一条变更去翻另一个版本段。
- 引用指向的**代码**与文档都在仓库内才成立；指向本机 scratch（截图、临时记录）的一律去掉路径、只留可读结论。
- 历史条目也按**当前事实**写 —— **只写了一半的描述同样算过期**（它读起来不像错的，没人会去查）；确需保留原委时在行尾标注 `【YYYY-MM-DD 修正：原文……】`。

## 2. 迭代与需求文档维护流程（集成：旧"迭代指南"）
**原则：不做 vN 副本**。每个主题一份当前态活文档（固定名、不带版本，永远描述现在）；变更走"更新记录 + CHANGELOG"；仅对外发版/破坏性里程碑才做只读快照。

| 环节 | 动作 |
|---|---|
| 需求进入 | 在 `01` 功能行标 `[in-progress]`；在对应文档底部"更新记录"追加一行（含日期时间与插件版本） |
| 涉及主题 | 更新对应活文档：加功能更新 01；动 UI 更新 03；动协议更新 04；动结构更新 02 |
| 发布 | 更新 `05` 的 ReleaseNotes/CHANGELOG，bump `package.json` 版本 |
| 快照（可选，仅发版/里程碑） | 复制到设计文档目录下的 `_archive/<version>/` 只读冻结，之后不回改 |
| 提案/ADR（可选，大变更） | 用 `docs/decisions/<YYYYMMDD>-<topic>.md`，定案后并入活文档 |

## 3. dsh 上游变更驱动（dsh 一升级，插件就可能有跟随需求）
完整机制见 `04` 的升级章节。此处仅列原则：每次 dsh 发布新版本 → 在 `04` 契约核对 → 判影响面（页面面=零影响 / 协议面=改 `src/dsh/` / 数据面=改投影渲染）→ 需改的记为一条跟随需求并跟踪状态 → 随插件版本发布。

## 4. 开发协作规范（集成：目录/命名/状态/版本控制）
### 4.1 目录结构（实际，勿照搬其它模板）
顶层分工：`src/`(宿主，协议层在 `src/dsh/`)、`webview/chat/`(聊天 UI，独立打包)、`dist/`(产物)、`release/`(vsix)、`scripts/`、`assets/`、`docs/`(活文档)、`tmp/`(进度/TODO)。
### 4.2 分层铁律
UI 不感知 dsh 协议字段；协议改动只进 `src/dsh/`；聊天 UI 经 `DshService`、上游网页经 `DshPanel` 的稳定接口。
### 4.3 命名
文件小写语义；函数/变量 camelCase；服务方法动词开头；协议常量 UPPER_SNAKE；dsh 封装与 wire 语义对齐。
导出函数名不携带 dsh 版本前缀（如 `workspaceList` 而非 `rc1WorkspaceList`）；每个方法适配的版本与上游接口写在其 JSDoc 里；dsh 小版本升级若协议不变，只需增补字段/方法。
以上禁的是**版本**前缀。**来源**前缀 `dsh` / `Dsh` 是另一回事：它标记「形状照搬上游、关联度高」的标识符（类型用 `Dsh`，字段/函数用 `dsh`），插件自有的 UI 与功能标识符不加，注释里也不写 dsh——为后续适配其它后端与插件独有功能留出命名空间。
### 4.4 状态管理
分三层：服务态归 `DshService`；端点与能力态归协议层的模块级状态；跨重启持久态走扩展 `globalState`（消费记录上限 500 条）。
### 4.5 质量门槛
改动需过 `pnpm run compile`（= `pnpm run check-types` + `pnpm run lint` + `pnpm run build:chat` + `node esbuild.js`）；打包用 `pnpm vsix`；动协议先更 `04`。
开发宿主不热加载：改完代码后验证前先 `Developer: Reload Window`；普通 VS Code 测试已安装扩展需“重打包 + 重装 + 重载”，流程见 `05`。
**观测代码与数据路径解耦（🔒）**：日志/追踪不得写进能中断数据流的位置 —— 序列化一律走**不会抛**的实现（`JSON.stringify(undefined)` 返回的不是字符串，直接接 `.slice()` 会抛），事件分发对**单条事件失败**要有容错边界（记一行、跳过该条，不让整轮失败）。理由：调试代码抛异常会让「数据没送到」伪装成上游问题或显示 bug，排查成本极高；且这类故障常只在打开调试开关时出现，极易误判。
### 4.6 版本控制 / 提交
分支：`main` 可发布基线 + `feature/*`/`fix/*`。提交用 Conventional：`feat/fix/refactor/docs/chore/build(deps): upgrade dsh to <v>`。

## 5. 维护提示
任何文档改动：更新其元数据 + 底部"更新记录"行。改文档不看备份（备份只存不管）。
